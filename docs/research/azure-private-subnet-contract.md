# Self-managed Azure Private Link: subnet contract (research, 2026-09-25)

**Scope:** upstream HyperShift source at `research/azure-private-contract` (base `fbaf59ae8f`), the [published private-cluster guide](https://hypershift.pages.dev/how-to/azure/deploy-azure-private-clusters/), [architecture](https://hypershift.pages.dev/reference/architecture/azure/privatelink/), [infrastructure reference](https://hypershift.pages.dev/reference/infrastructure/azure-self-managed/), and merged upstream PRs. This is **not** evidence of what a particular customer has installed.

## What is documented and implemented

| Resource / path | Contract and observed implementation |
| --- | --- |
| Guest Private Endpoint (PE) | The published architecture says the CPO creates a PE **in the guest subnet** (architecture source: `docs/content/reference/architecture/azure/privatelink.md:99-110,121-130`). The observer copies `HCP.spec.platform.azure.subnetID` to `AzurePrivateLinkService.spec.guestSubnetID` (`control-plane-operator/controllers/azureprivatelinkservice/observer.go:164-172`); the CPO creates the PE using exactly that ID (`control-plane-operator/controllers/azureprivatelinkservice/controller.go:528-569`). The HC `subnetID` is documented as the existing node subnet and is immutable (`api/hypershift/v1beta1/azure.go:417-440`). `--subnet-id` supplies it (`cmd/cluster/azure/create.go:98-105,390-396`); `--vnet-id` supplies the guest VNet. **No independently selectable guest PE subnet appears in this path.** A separate PE-only subnet is not a shipped promise; choosing a separate NodePool subnet does not redirect the PE. |
| Management ILB frontend | The private `private-router` Service is `type: LoadBalancer` with the Azure *internal* annotation (`control-plane-operator/controllers/hostedcontrolplane/infra/infra.go:438-475`; `control-plane-operator/controllers/hostedcontrolplane/ingress/router.go:61-77`), not a guest VNet LB. HyperShift does **not** annotate it with `azure-load-balancer-internal-subnet` here; [Azure cloud-provider documentation](https://cloud-provider-azure.sigs.k8s.io/topics/loadbalancer/) says that, absent that annotation, its cloud-config subnet is used. The CPO observes the assigned Service ingress IP (`control-plane-operator/controllers/azureprivatelinkservice/observer.go:94-105,164-172`); HO finds the Azure LB frontend by that IP and reads its actual subnet (`hypershift-operator/controllers/platform/azure/controller.go:378-413`). Thus the precise management subnet is determined by the management cluster's LB provisioning, **not** `HC.spec.platform.azure.subnetID`; verify the actual frontend rather than guessing from the guest subnet. |
| PLS NAT | The [published guide, Step 1](https://hypershift.pages.dev/how-to/azure/deploy-azure-private-clusters/#step-1-prepare-the-nat-subnet) explicitly requires a dedicated **management VNet**, same-region NAT subnet with `privateLinkServiceNetworkPolicies` disabled, then passes its resource ID via `--endpoint-access-private-nat-subnet-id` (source: `docs/content/how-to/azure/deploy-azure-private-clusters.md:47-113,247-273`). The CLI only checks ID syntax/resource type (`cmd/cluster/azure/create.go:203-212`), stores it in `HC.spec.platform.azure.private.privateLink.natSubnetID` (`:400-412`), and HO uses that ID for PLS NAT IP configuration while attaching the PLS to the discovered management ILB frontend (`hypershift-operator/controllers/platform/azure/controller.go:299-350`). Azure's [PLS specification](https://learn.microsoft.com/en-us/azure/private-link/private-link-service-overview) distinguishes **service-provider NAT IPs** from the consumer PE IP, and requires PLS, VNet, and Standard LB to share a region. The NAT subnet is **not** the guest PE subnet. |
| API versus OAuth | Private API with `Route` publishing uses `private-router` → management ILB → PLS → guest PE, and guest private DNS resolves API to PE (`control-plane-operator/controllers/hostedcontrolplane/infra/infra.go:246-287,465-475`; `control-plane-operator/controllers/azureprivatelinkservice/controller.go:864-924`). The Azure CLI defaults KAS to Route for Private topology, OAuth to Route, and allows `--oauth-publishing-strategy=LoadBalancer` (`cmd/cluster/azure/create.go:148-154,498-505`; `cmd/cluster/core/create.go:1097-1106`). OAuth **Route** shares the private-router path; OAuth **LoadBalancer** creates a separately annotated internal `oauth-openshift` Service and a second observed PLS/guest PE, with its own OAuth DNS A record (`control-plane-operator/controllers/hostedcontrolplane/oauth/service.go:59-78`; `control-plane-operator/main.go:658-683`; `control-plane-operator/controllers/azureprivatelinkservice/controller.go:864-924`). Both observers still copy the **same** HC guest subnet ID (`observer.go:164-172`). A private KAS `LoadBalancer` strategy instead has a separate private KAS Service (`infra/infra.go:288-295`); do not equate that Service with the PLS observer, which watches `private-router` (and optionally OAuth), not the KAS Service (`control-plane-operator/main.go:658-683`). |

## Version/history and limits of the claim

- Initial self-managed Private Link design, manual validation and docs landed in [PR #7821 (merged 2026-03-31)](https://github.com/openshift/hypershift/pull/7821). Separately routed OAuth LB support landed in [PR #8148 (API)](https://github.com/openshift/hypershift/pull/8148) and [PR #8149 (merged 2026-04-08)](https://github.com/openshift/hypershift/pull/8149). Private-without-external-DNS installation was later reported broken and fixed in [PR #9171 (merged 2026-08-06)](https://github.com/openshift/hypershift/pull/9171). These are upstream integration/fix dates, **not customer delivery dates**.
- **Docs/code drift, not proof of a customer regression:** the published infrastructure reference still calls the management NAT subnet “User (pre-existing)” (`docs/content/reference/infrastructure/azure-self-managed.md:183-195`), but current HO code *also* auto-creates one in the **ILB frontend VNet** when `natSubnetID` is empty (`hypershift-operator/controllers/platform/azure/controller.go:299-315,760-824`; introduced in [commit `16499babb8`](https://github.com/openshift/hypershift/commit/16499babb8cf9ab5a059bb48c5209c8ef0aad503), included in [PR #8149](https://github.com/openshift/hypershift/pull/8149)). The API comments incorrectly say “HC's VNet” (`api/hypershift/v1beta1/azure.go:778-790`; `api/hypershift/v1beta1/azureprivatelinkservice_types.go:114-122`), while executable code keys off the management ILB subnet. Auto-allocation scans **only** unused `10.0.1.0/24`…`10.0.255.0/24` blocks and does not query the VNet's address prefixes (`controller.go:826-864`): it can fail on another address space or with no suitable /24. The documented explicit management NAT subnet avoids depending on that fallback. Current e2e setup still supplies an explicit NAT ID (`test/e2e/v2/lifecycle/azure.go:75-83,138-157`).
- The [published guide](https://hypershift.pages.dev/how-to/azure/deploy-azure-private-clusters/) says **“planned as a Tech Preview feature in OCP 4.22”**, not that every 4.22 or client installation contains these changes (`docs/content/how-to/azure/deploy-azure-private-clusters.md:15-17`). The published architecture's single-PE/single-PLS drawing predates OAuth LB and should not be read as excluding the later optional second pair (`docs/content/reference/architecture/azure/privatelink.md:41-74,144-150`; [PR #8149](https://github.com/openshift/hypershift/pull/8149)). Neither docs nor PRs establish the customer's HO/CPO/CLI image digests, OCP payload, topology, chosen publishing strategies, subnet IDs, or whether a PE was created. **Obtain those version/resource facts before labeling observed placement a regression or promising a remediation.**
