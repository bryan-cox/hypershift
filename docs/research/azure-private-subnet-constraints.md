# Azure private endpoint subnet placement and isolation constraints

Scope: self-managed Azure HyperShift; researched 2026-09-25. **Azure facts** below are Microsoft documentation/API contracts; **HyperShift observations** describe this checkout, not Azure requirements. No live deployment was tested.

## Azure facts

| Component | Placement and policy | Isolation / operational consequence |
| --- | --- | --- |
| Guest Private Endpoint (PE) | Allocates a NIC/IP in a chosen **guest VNet subnet**, in the **same region and subscription as that VNet**, but the Private Link target may be in another region/subscription/tenant. Multiple PEs may share a subnet; a dedicated subnet is **not required**. A **delegated** subnet cannot host a PE. [PE overview](https://learn.microsoft.com/en-us/azure/private-link/private-endpoint-overview), [FAQ](https://learn.microsoft.com/en-us/azure/private-link/private-link-faq), [delegation](https://learn.microsoft.com/en-us/azure/virtual-network/subnet-delegation-overview). | `privateEndpointNetworkPolicies` defaults to disabled; enable `NetworkSecurityGroupEnabled`, `RouteTableEnabled`, or `Enabled` on the **PE subnet** if NSG/UDR filtering of PE traffic is needed. This setting affects **all PEs in that subnet**, not ordinary resources. Clients in the VNet, peered VNets, or on-prem via VPN/ExpressRoute can reach an approved PE if DNS/routing/security permit. DNS must resolve the service hostname to its PE IP. [PE policy](https://learn.microsoft.com/en-us/azure/private-link/disable-private-endpoint-network-policy), [PE overview](https://learn.microsoft.com/en-us/azure/private-link/private-endpoint-overview). |
| Management internal load-balancer (ILB) frontend | An ILB has a private frontend IP from the provider VNet; it is **not** the PLS NAT IP. The frontend and LB backends must be in one VNet (not necessarily one subnet). The IP must be free in its selected subnet. A Standard LB with NIC-based backend pool is required for standard PLS (not Basic or IP-based backend pool). [LB components](https://learn.microsoft.com/en-us/azure/load-balancer/components), [AKS ILB subnet example](https://learn.microsoft.com/en-us/azure/aks/internal-lb#specify-a-different-subnet), [PLS limitations](https://learn.microsoft.com/en-us/azure/private-link/private-link-service-overview#limitations). | A private ILB is not an internet endpoint, **but is not by itself restricted to Private Link consumers**: clients with a network path to that private IP can potentially connect. Govern direct frontend/backend reachability with VNet routing and NSGs, not just PLS visibility. [LB components](https://learn.microsoft.com/en-us/azure/load-balancer/components), [NSGs](https://learn.microsoft.com/en-us/azure/virtual-network/network-security-groups-overview). |
| Management PLS source-NAT subnet | A PLS references a Standard LB frontend and chooses NAT IP(s) from **any subnet of the provider VNet**; the PLS, LB, and VNet must be in the same region. A **dedicated NAT subnet is not required** by Azure. Explicitly set `privateLinkServiceNetworkPolicies=Disabled` on the **NAT subnet** (distinct from the PE policy above). The setting only exempts the PLS; NSG rules still govern other resources in that subnet. Allow spare IPv4 capacity (Microsoft recommends at least eight available NAT IPs; up to eight NAT configurations per PLS). [PLS overview](https://learn.microsoft.com/en-us/azure/private-link/private-link-service-overview), [FAQ](https://learn.microsoft.com/en-us/azure/private-link/private-link-faq), [PLS subnet policy](https://learn.microsoft.com/en-us/azure/private-link/disable-private-link-service-network-policy). | PLS performs provider-side SNAT: backends see a provider NAT IP, **not the guest client IP** (unless the backend understands optional PROXY v2). Plan backend NSGs for NAT-source traffic and LB health probes; a dedicated NAT subnet is an isolation/capacity recommendation, not an Azure prerequisite. Azure subnets must be non-overlapping within the VNet; five IPs per subnet are reserved. [PLS overview](https://learn.microsoft.com/en-us/azure/private-link/private-link-service-overview), [subnet sizing](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-manage-subnet). |

**Permissions and approvals:** PE creation requires access to its guest subnet (`subnets/read`, `subnets/join/action`) and `privateEndpoints/read,write`; subnet `write` is separately needed to change PE policies. PLS creation requires `privateLinkServices/read,write`, LB read/write and subnet access; subnet `write` is separately needed to disable PLS policies. Scope grants to the guest and management resources actually used; network roles do not imply automatic approval of arbitrary target services. An alias-based PE request uses manual connection semantics, although a guest subscription in the PLS **visibility and auto-approval** lists can be approved automatically. Only approved connections carry traffic; visibility/approval govern consumers, **not** direct ILB reachability. [Azure Private Link RBAC](https://learn.microsoft.com/en-us/azure/private-link/rbac-permissions), [PE approval/alias](https://learn.microsoft.com/en-us/azure/private-link/private-endpoint-overview#connect-by-using-an-alias), [PLS access](https://learn.microsoft.com/en-us/azure/private-link/private-link-service-overview#control-service-access).

**Separate API vs OAuth endpoints:** Azure binds a PLS to a *specific* Standard LB frontend, and one PE connects to **one** PLS; multiple PLS instances can use **different** frontends of one Standard LB. LB rules distinguish TCP/UDP frontend IP/port, not HTTP hostnames. Therefore independent API/OAuth PE IPs are feasible with distinct ILB frontends and PLS/PE connections (or separate LBs). Two DNS records pointing to separate PEs **backed by the same shared router frontend do not isolate the services**: routing and backend policy would still need to enforce the separation. A Route behind a shared ingress/router is host-level routing on the same frontend, not an Azure network boundary. [PLS overview](https://learn.microsoft.com/en-us/azure/private-link/private-link-service-overview#details), [FAQ](https://learn.microsoft.com/en-us/azure/private-link/private-link-faq), [LB rules](https://learn.microsoft.com/en-us/azure/load-balancer/components#load-balancer-rules).

## HyperShift observations / implications (not Azure mandates)

- The CPO observes the `private-router` internal LB and, **only for OAuth `LoadBalancer` publishing**, also the `oauth-openshift` internal LB; each observed Service gets a PLS CR, then a guest PE in `AzurePlatform.SubnetID`. See [`control-plane-operator/main.go`](../../control-plane-operator/main.go), [`observer.go`](../../control-plane-operator/controllers/azureprivatelinkservice/observer.go), [`controller.go`](../../control-plane-operator/controllers/azureprivatelinkservice/controller.go). This currently **reuses the worker subnet** for PEs; a separately selectable guest PE subnet is not exposed by that observer.
- The default `private-router` CR writes `api-<cluster>` and (absent a sibling OAuth CR) `oauth-<cluster>` DNS records to the **same PE IP**; with OAuth `LoadBalancer`, the sibling OAuth CR writes OAuth to its **own** PE IP. This supports separating OAuth at the Azure endpoint level, but a Route strategy leaves OAuth on the router path. A private API `LoadBalancer` Service exists (Azure port 7443), yet the Azure PLS observer does **not** watch it: distinct PLS/PE/DNS wiring for that API LB would require product work, not just a subnet or DNS change. See [`infra.go`](../../control-plane-operator/controllers/hostedcontrolplane/infra/infra.go), [`kas/service.go`](../../control-plane-operator/controllers/hostedcontrolplane/kas/service.go), [`oauth/service.go`](../../control-plane-operator/controllers/hostedcontrolplane/oauth/service.go), [`controller.go`](../../control-plane-operator/controllers/azureprivatelinkservice/controller.go).
- The HO uses the configured NAT subnet or auto-creates one in the discovered ILB VNet; the CPO/HO credentials and LB placement must be checked separately. Microsoft documents an `azure-load-balancer-internal-subnet` Service annotation **for AKS**, but that does **not** establish support/behavior for this OpenShift management cluster. See [`HO controller`](../../hypershift-operator/controllers/platform/azure/controller.go), [AKS ILB guidance](https://learn.microsoft.com/en-us/azure/aks/internal-lb#specify-a-different-subnet).
- Documentation correction to consider separately: [`deploy-azure-private-clusters.md`](../content/how-to/azure/deploy-azure-private-clusters.md) says Azure **requires a dedicated** NAT subnet. Microsoft explicitly says it **does not** ([FAQ](https://learn.microsoft.com/en-us/azure/private-link/private-link-faq)); dedicating it can still simplify isolation and capacity planning. This note does not change published docs.
